Metrics dashboard

Inspect storage, throughput, and latency from an embedded dashboard.

Mount the handler

MetricsHandler serves a dashboard bundled into the binary, using plain HTML, CSS, and JavaScript with automatic light/dark styling. Mount it with net/http:

mux := http.NewServeMux()
mux.Handle("/debug/dot/", http.StripPrefix("/debug/dot", db.MetricsHandler()))
if err := http.ListenAndServe("127.0.0.1:8080", mux); err != nil {
    log.Print(err)
}

The page opens a WebSocket using github.com/coder/websocket and receives the current metrics immediately, then once per second. Configure the push interval with db.MetricsHandler(dot.WithMetricsInterval(250*time.Millisecond)); the interval must be positive. Register the mount path with a trailing slash and strip the prefix without that slash, as shown above, so the handler receives paths beginning with /.

Storage metrics

Disk usage scans filesystem allocation under the database path at each snapshot, outside shard locks. Storage counters do not scan index slots:

MetricMeaning
On-disk sizeAllocated filesystem blocks under the database path, including logs, META, LOCK, temporary compaction files, and directories. Sparse holes do not count; child symlinks are not followed and hard links count once. Filesystem-wide overhead is not attributable to this path.
Obsolete bytesRetained log bytes no longer referenced by the index, including replaced records and tombstones. Compaction reclaims this history.
EntriesKeys currently in the index. Expired keys remain counted until pruning; this is not an exact live-key count.
Index mmapMapped address space for this database's anonymous index allocations, including any previous mapping retained after a failed unmap. Includes pages not resident in RAM; this measures index mapping size rather than resident memory.

Operation metrics

The operations table reports Get, Set, Delete, and Update throughput, mean latency, and approximate p99 latency. Select table values to graph them; series with matching units can be compared. P99 lines are dashed. Rates display as 0.24 or 4.4K under the Ops/sec header, with two decimal places below 1,000 and one in compact notation. Latencies keep two decimal places in their displayed unit. Rates and latencies use a trailing ten-second window sampled at one-second resolution. The boundary can extend the window by up to one sampling interval; rates divide by the actual elapsed time. Initial readings use the shorter time since collection began. Mean latency is total duration divided by timed calls; p99 comes from the combined window histogram, rounding up by at most 12.5%. Empty windows display zero throughput and unavailable latency. Small sample counts make p99 less stable.

Operation instrumentation is enabled only while WebSocket viewers are connected. Counters and histograms are shared across all handlers and viewers on the DB. Disconnecting the last viewer disables recording and discards the window; a reconnection starts fresh. With no viewers, each operation only checks whether recording is enabled. Calls already in progress may finish recording to the old session. All API calls count, including errors, misses, and unchanged writes; Update counts once. Latency includes lock waits, callbacks, and requested syncs. Counters are maintained per shard, require no per-call allocations, and snapshots are approximate under concurrent calls rather than transactional.

Latency collection

Timing is enabled by default. For throughput without clock reads or histogram updates, use db.MetricsHandler(dot.WithMetricsLatency(false)). Timing remains active while any connected handler requests it. Histograms use bounded memory (about 1 MiB for the default 64 shards, plus window readings), independent of operation volume. Clock reads and counter/histogram updates occur on the operation path; window aggregation and percentile calculation run in dashboard collection.

Sampling and stale readings

Snapshots briefly try each shard's read lock. Busy shards retain their previous readings; until every shard has been sampled, the UI waits before showing totals. Shards are sampled independently, so totals are not a point-in-time database snapshot. If a disk scan fails, the previous disk reading is retained and marked stale; the first complete scan is required before showing totals. Disk scans add work proportional to the number of files.

Browser history

Collection is shared by viewers of the same handler and runs only while viewers are connected. The server keeps current readings only. The browser records graph history in a ring capped at 20,000 snapshots for last-minute, last-hour, and all retained-history views; older samples are evicted and reloading clears it. At the default interval this retains roughly 5.5 hours. Rendering preserves per-pixel extrema. Metric buttons support multiple selections with matching units on a shared scale; hovering shows sample values, including raw nanoseconds for latency. Closing the database stops its WebSockets. HTTP server shutdown and any authentication middleware remain with the application.

Try the dashboard

The dashboard reads Dot's version from the binary's Go build metadata. Tagged dependencies show their release version without extra build flags. Untagged commits show dev · <short hash>; local builds with uncommitted changes append · dirty. Local replacements or missing metadata show dev.

Run go run -buildvcs=true ./fiddle for a demo with a temporary database under /tmp and a repeating workload. See fiddle/README.md for usage.
