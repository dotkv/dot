Storage & recovery

Understand layout, durability, recovery, and background maintenance.

Database layout

New databases default to 64 key shards. Pass WithShardCount(count) to Open to choose a power of two between 1 and 1024:

db, err := dot.Open("data", dot.WithShardCount(16))

META stores the shard count, format version, segment ID and size bit counts, and record alignment. It is synced and atomically published before shard initialization. Reopening without WithShardCount uses the stored count. An explicitly different count returns an error wrapping ErrMigrationRequired; changing shard routing requires rewriting the database. Unsupported versions or segment layouts also return ErrMigrationRequired before log recovery. Automatic data migrations are not supported.

An empty database directory can be initialized. A nonempty directory without META, including a database created by an older release, is rejected because its layout cannot be established safely. Empty or malformed metadata is also rejected rather than replaced. WithShardCount has no effect on key operations.

Single-process access

Open takes an exclusive file lock on <path>/LOCK and holds it until Close. A second Open of the same path — from any process, or again in the same process — fails with an error wrapping ErrDatabaseLocked. The kernel releases the lock if the process dies, so it can never go stale. File locking is not reliable on NFS; use local storage.

Recovery

Open replays each shard's log segments in order to rebuild its index, applying sets, deletes, and expirations. It resumes appending at the end of the newest segment. An incomplete final record in that segment is truncated; checksum failures, invalid records, or incomplete records in older segments fail opening. Segment IDs wrap after 1048575. Published filenames must form one contiguous run around that ring, leaving at least one vacant ID. Open infers the newest segment from this gap and rejects layouts with multiple gaps or no vacant ID. Recovery scans all retained log records; checkpoints and a manifest are not used.

Each shard index starts with 1 << 14 eight-byte slots: 128 KiB per shard, or 8 MiB of initial anonymous mmap storage at the default 64 shards. Resident memory depends on pages touched. Each slot contains three metadata bits, a 19-bit hashtag, a 20-bit segment ID, and a 22-bit offset in 16-byte units within the segment's 64 MiB start range. The hashtag supports growth without reading keys up to 1 << 33 slots per shard. At 75% occupancy, the theoretical index ceiling is 6,442,450,944 entries per shard, or 412,316,860,416 across the default 64 balanced shards; RAM and retained log space can impose lower limits.

Indexes double at 75% occupancy. During background maintenance, an index below 25% occupancy shrinks by half, down to the initial 128 KiB per shard. Each pass halves at most once. Shrinking merges runs using only in-memory slot metadata: it performs no database file reads and takes linear time in the old capacity, like growth. The rebuild holds that shard's exclusive lock and briefly retains both mappings. Allocation failure preserves the existing index; failed unmaps retain the old mapping for a later maintenance retry. Shrink failures do not fail foreground mutations or disable disk compaction scheduling.

Failed writes that made partial progress are truncated back to the last complete record, and the repair is synced. If rollback fails, further appends fail until the database is reopened. Successful writes are not synced individually; pass WithSync(true) to Open (or to a single Set/Delete/Update) to fsync the log before the call returns.

Compaction

Successful mutations queue background compaction when more than 33% of a shard's encoded log bytes are obsolete and at least 1 MiB is obsolete. A single worker serves a bounded queue with at most one queued request per shard. Checks use incremental byte counters, without scanning segments or adding reads to the write path. Compaction holds one shard's exclusive lock for its pass; other shards can continue serving requests.

Pass WithCompactionThreshold(ratio, minObsoleteBytes) to Open to configure the state trigger. For example, WithCompactionThreshold(0.4, 1<<20) requires more than 40% obsolete bytes and at least 1 MiB of obsolete data in that shard. The second argument is bytes, replacing the previous record-count unit. The ratio must be finite and in [0, 1); a zero minimum is allowed. The option has no effect when passed to Set.

Both thresholds count complete encoded records: the 21-byte header, key, value, and alignment padding. Obsolete bytes are total retained record bytes minus bytes referenced by the index. Deletes count toward retained history until compaction removes them. Expired records become obsolete when pruned from the index. Counters are rebuilt from existing logs during recovery. Index slots remain eight bytes.

A larger minimum trades more retained history for fewer compaction passes and sync operations. The minimum applies per shard: 1 MiB across 64 shards amounts to roughly 64 MiB of possible obsolete history before considering the ratio, queued work, and live data. This is a scheduling threshold, not a disk-space cap.

Every ten seconds, the worker also checks shards with tracked expirations or pending cleanup. It prunes expired index entries, then applies the configured obsolete-byte ratio without the state trigger's minimum byte count. Every shard without a queued pass also checks for sparse indexes and retained mappings, even when disk compaction is unnecessary. Queued and explicit compaction passes check for shrinking after they finish using index positions. Failed disk passes wait for the ticker to retry, including when pruning removed the last expiration entry. Recovery queues eligible history, already expired records, and unfinished packing without waiting for another write. Pending passes complete even below the configured thresholds.

The pass first removes obsolete history from oldest to newest, preserving delete and expiration semantics. It then packs current records toward the existing head and removes empty files only from the oldest boundary, keeping one filename gap. Values retain their encodings and expiration times.

Replacement records use a 64 KiB output buffer, flushed before the temporary NNNNNNN.log.compact file is synced and atomically renamed over its published log. Multi-segment passes first sync the active head before discarding older history. A lone head needs only the synced replacement; its original stays intact until rename. The directory is synced before retiring any sources. An interrupted pass can leave identical records in source and destination files; replay handles those normally. Unpublished temporary files are discarded during recovery. Compaction needs temporary space for one output segment and holds relocation information proportional to the shard's index size.

Record format

The 21-byte record header is [crc32 4][type 1][keylen 4][vallen 4][expiration 8], followed by the key and value, then zero padding to a 16-byte boundary. Every record starts at a 16-byte-aligned offset. Header integers are big-endian. The checksum covers the type, lengths, expiration, key, and value, excluding padding; recovery also validates that padding is zero. Type tags are fixed:

TagTypeValue payload
0x01DeleteEmpty; expiration must be zero
0x02[]byteAny length, including empty
0x03int648 little-endian bytes
0x04uint648 little-endian bytes
0x05float648 little-endian bytes containing its IEEE 754 bits
0x06bool(false)Empty
0x07bool(true)Empty
0x08stringAny length, including empty

Both boolean tags have the logical type bool. Empty bytes, false, true, and deletes remain distinct records. Invalid tags or payload lengths return an error wrapping ErrInvalidValue. Compaction and recovery preserve value types and exact floating-point bits. Unchanged writes compare type, payload, and expiration.

With 16-byte keys, eight-byte values occupy 48 bytes per record (three padding bytes), and 1 KiB values occupy 1,072 bytes (eleven padding bytes).
