Storage & recovery

Choose durability settings and manage a database in your application.

Database access

Keep the database on local storage and share one *dot.DB across goroutines. A second Open of the same path, including from the same process, fails with an error wrapping ErrDatabaseLocked. Check it with errors.Is(err, dot.ErrDatabaseLocked). The lock is released when the database closes or the process exits.

Durability

WithDurability selects a default mode for Open, or overrides it for a single Set, Update, Add, Sub, or Delete:

db, err := dot.Open("data", dot.WithDurability(dot.Sync))
ModeBefore returning
dot.Buffer (default)Copies the record into a 64 KiB buffer per active shard.
dot.WriteWrites the record to the file, using the OS page cache.
dot.SyncWrites and fsyncs the shard log.

Buffered records flush without fsync when the buffer fills or within 100 ms of the first pending write. Later writes do not postpone the deadline, and records larger than 64 KiB write directly. Close, log rotation, background cleanup, and a Write or Sync call on the same shard also drain pending bytes (even for unchanged values or missing deletes); Sync then fsyncs that shard. A background flush failure blocks further mutations in that shard and is returned by subsequent mutations and Close.

A rejected WithCondition returns ErrConditionFailed without applying the mutation's durability request or flushing earlier buffered writes.

Reads, atomic updates, and scans see buffered writes immediately. A process crash can lose buffered writes, while Write and flushed Buffer records still lack a power-loss guarantee. Use dot.Sync when writes must survive power loss before returning.

Reopening and recovery

Open recovers existing data automatically. Startup time grows with the retained log history. An incomplete final write is discarded; checksum failures and other corrupt records cause opening to fail.

Back up the entire database directory after closing it. A copy made while writes or background cleanup are running is not a consistent backup. Keep the directory's metadata and data files together.

Database options

New databases default to 64 shards. Choose a different count at creation if needed:

db, err := dot.Open("data", dot.WithShardCount(16))

The count must be a power of two from 1 to 1024. Reopening without this option uses the stored count; passing a different count fails because changing it requires rewriting the database. The META file stores and checksums the disk-format version, shard count, and segment layout, and is validated before any shard log is recovered.

Background cleanup

Dot automatically reclaims overwritten, deleted, and expired data, and shrinks sparse shard indexes in the background. Expired keys read as missing immediately, while their disk space is reclaimed later. Cleanup can temporarily block operations on the shard being processed and needs room for a temporary output file.

The defaults suit most applications. To change when overwritten and deleted history triggers cleanup:

db, err := dot.Open("data",
    dot.WithCompactionThreshold(0.4, 1<<20),
)

This queues cleanup after a write when more than 40% of a shard's retained data is obsolete and at least 1 MiB is obsolete. The defaults are 33% and 1 MiB per shard. The ratio must be in [0, 1); the minimum can be zero. Periodic expiration sweeps use the ratio without the byte minimum. Larger thresholds trade more disk usage for less frequent cleanup. The dashboard shows disk usage and obsolete bytes.
